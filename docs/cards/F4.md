# F4. Show readiness and request sign-only payment approvals

Live issue: [#10](https://github.com/nefalos-tech/OneTab/issues/10)

This is the repository copy of the implementation brief. The live issue and board own status and discussion. Update both copies when the task scope changes.

Before implementation, read the [architecture](../architecture.md), [shared contracts](../contracts.md) and [development guide](../development.md).

Owner: @Quantomz
Lane: Frontend
Estimated effort: 3 hours. This is a planning budget, not a delivery guarantee.
Phase: Integrate

## Outcome

Each payer understands and authorizes their contribution to the same complete payment.

## Start and handoffs

Build all Ready/Signing/Signed states using fixtures, then integrate the payment validator and routes.

Implementation prerequisites: [F2](https://github.com/nefalos-tech/OneTab/issues/8), [F3](https://github.com/nefalos-tech/OneTab/issues/9)

Needed for final integration: [P2](https://github.com/nefalos-tech/OneTab/issues/2), [P3](https://github.com/nefalos-tech/OneTab/issues/3), [B3](https://github.com/nefalos-tech/OneTab/issues/15).

## Work

- [ ] Show Ready as coordination only. Expose the organizer's start action only when the room is full and everyone is ready.
- [ ] Fetch SigningPayload and validate its full plan with P2's validator before opening the wallet prompt.
- [ ] Prominently show the payer's share, seller, total and network. Explain that signing covers the complete transaction.
- [ ] Collect the wallet's sign-only result and upload its signature to the current attempt.
- [ ] Poll the shared snapshot and display Ready and Signed separately. Prevent duplicate prompt clicks.
- [ ] Handle wallet rejection and account changes without implying that an existing signature was revoked.
- [ ] After a refusal in the wallet, offer **Decline payment** as the notice's follow-up. Declining is never automatic, and a refusal alone sends nothing. Added on 2026-11-07.

The browser checks each signing payload against the payment its screen shows, field by field and against the equal split, before the wallet opens. Payments' byte check plugs into one seam in `src/client/payment-check.ts`, and P3's check of the signature the wallet returns plugs into a second seam beside it. Until P2 and P3 export them, both seams answer that the payment can't be checked yet, so a live Approve opens no wallet and uploads nothing. The wallet prompt itself waits for P1's adapter in `src/lib/wallet/live.ts`. The PR that wires P2's export adds `@solana/kit` and `@solana-program/token` at the versions P1 recorded and proves the bundle with `next build`.

Sample data stays static. A sample payer sees the approval summary, Ready and Approve still say they aren't connected in sample data, and Decline never appears there. The sample wallet never approves a payment.

Until P1, P2, B3 and the payment routes land, the evidence is unit tests with a stubbed fetch and a scripted wallet, the e2e suite's three browsers on one scripted room, and a browser run of the signed-in paths against stand-ins for the wallet adapter and the byte check. The signed-in three-wallet run on the hosted Devnet app belongs to F6. A byte-level tamper test needs Payments' 32-byte fixtures.

## Done when

- [ ] Three screens show coherent participant readiness and signature status.
- [ ] A tampered payment plan never reaches the wallet signing prompt.
- [ ] The browser never broadcasts separate contribution payments.
