## Outcome

A connected wallet establishes the correct authenticated identity without authorizing a payment.

## Start and handoffs

Implement the WalletBridge interface and disconnected/unsupported states against a fake wallet while P1 and B2 progress.

Implementation prerequisites: [F1](https://github.com/nefalos-tech/OneTab/issues/7)

Needed for final integration: [P1](https://github.com/nefalos-tech/OneTab/issues/1), [B2](https://github.com/nefalos-tech/OneTab/issues/14).

## Work

- [ ] Integrate the wallet and pinned packages proved by P1. Keep connect, sign challenge and sign transaction as separate operations.
- [ ] Use B2's one-time authentication challenge and server session.
- [ ] Handle missing wallet, wrong network, rejected authentication and disconnected state.
- [ ] Clear stale identity and payment prompts when the wallet account changes.
- [ ] Verify that the payment operation is sign-only; the final shared payment is submitted by the coordinator.
- [ ] Add the sample wallet, an in-page stand-in that runs every connect and sign-in path in sample data without Phantom. Added on 2026-11-07.
- [ ] Prove the identity rules with an exhaustive test that drives the session state machine through every short sequence of wallet events. Added on 2026-11-07.

The sample wallet and the live seams came first, so P1's adapter and B2's routes plugged in without changing the screens. The live bridge is `standardBridge` in src/lib/wallet/standard.ts, on the four Wallet Standard packages at the versions P1 recorded. It connects Phantom, signs B2's exact challenge and verifies the signature before the server sees it, and asks the wallet only to approve a payment, never to send it. Unit tests with keyed fake wallets and a fake Wallet Standard wallet in the e2e suite prove it. No real Phantom run has happened yet. [The live wallet evidence](../evidence/live-wallet.md) lists what is proven and the steps for the real-wallet check.

## Done when

- [ ] The supported desktop wallet connects and the authenticated address matches the selected account.
- [ ] Switching accounts cannot retain the previous payer's session or Ready state.
- [ ] Rejecting authentication causes no payment transfer.
