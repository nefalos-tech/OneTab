## Outcome

All three owners can build against the same shapes without waiting for complete implementations.

## Start and handoffs

Start immediately. Publish the minimal contract and example responses within the first 30 minutes, before completing the schema.

Implementation prerequisites: None. Start immediately.

## Work

- [ ] Define RoomSnapshot, SigningPayload, WalletBridge boundary and AttemptStore with input from the other owners. Amounts use integer-unit decimal strings; binary bytes use base64.
- [ ] Create fixtures for open/full/ready/signing/submitting/confirmed/failed/expired/unresolved. Mark every fixture as test data.
- [ ] Model immutable checkouts, stable participant slots, attempts, per-attempt signatures and observed receipts.
- [ ] Enforce unique wallet per checkout, bounded slot count, unique signer per attempt, and at most one active/unresolved attempt per checkout.
- [ ] Document the API paths, error shape and who owns each shared file. Backend owns contract changes; coordinate changes with consumers.
- [ ] Design RLS/grants for server-owned writes and authenticated wallet-session checks. Administrative database credentials stay on the server.

## Done when

- [ ] Frontend can render fixtures and payment code can use a fake AttemptStore immediately.
- [ ] The migration can be applied to the chosen development database and records survive a restart.
- [ ] Illegal duplicate participants, signatures and active attempts are rejected.
