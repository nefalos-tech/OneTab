## Outcome

Participants see the confirmed result or an accurate explanation of what remains unresolved.

## Start and handoffs

Build pending, failed, expired, unresolved and confirmed views against fixtures before the real RPC flow is ready.

Implementation prerequisites: [F3](https://github.com/nefalos-tech/OneTab/issues/9), [F4](https://github.com/nefalos-tech/OneTab/issues/10)

Needed for final integration: [P4](https://github.com/nefalos-tech/OneTab/issues/4).

## Work

- [ ] Show pending, confirmed, failed, expired and unresolved as distinct states from the server.
- [ ] Render a receipt only for confirmed success. Include seller, total, payer shares, transaction reference and Devnet explorer link.
- [ ] Restore the existing attempt after reload. Continue checking the same transaction after connection loss.
- [ ] Allow restart only when the server says the prior attempt is safely resolved and fresh approvals are required.
- [ ] Explain insufficient USDC/SOL and rejected prompts with a next action. Do not display a misleading successful or canceled state.

The result screen is a pure view of the public room. A receipt shows only when the room is paid and the receipt names the attempt's own transaction reference, this checkout's seller and total, and every share in spot order. Anything less reads Finalizing, and the explorer link is built from the reference. A failed payment's reason comes from the stop reasons in `src/client/catalog.ts`: network rejected when it was sent, else the room's error code, else the cause this page's own Start or Try again heard for that exact attempt, else a line that says it stopped before it was sent. Try again runs the same start path as Start, naming the attempt it replaces, and is offered only to the organizer of a failed or expired attempt with `canRetry`. A success moves everyone to the room, where a new attempt needs every approval again.

Until F2's wallet adapter, P4, B4 and handoff H1 land, the evidence is unit tests with a stubbed fetch, the e2e suite on the fake API's scripted rooms, and a browser run of the signed-in organizer's paths against a stand-in API. A live 422, a live retry, a real receipt and H1 in the hosted app are not run yet. The PR uses `Refs #11`, and this card stays open until that live proof exists.

Handoffs from F5:

- H1, B3 (@SophiaChua). Project `observed_error` as `error.code` when it is an `ErrorCode`, and `INVALID_PAYMENT` otherwise (`b3_rooms.sql:71`). Never emit any other value, because the server parses rooms with the client parser and one unknown code fails every room read. Then every viewer sees the cause with no client change. It also tells anyone with the link that a payer was underfunded, though not which one, so spec.md records that choice first.
- H2, B3. Coalesce the receipt subquery (`b3_rooms.sql:72-73`), so a missing receipt row keeps the attempt with `receipt: null` instead of dropping it.
- H3, Payments (@kyusuku) and B4. Resolve a declined attempt, or a signing attempt past its blockhash, as `expired` with `safelyResolved` once it can't land, and wire `backendAssurance` so `expired` is reachable.
- H4, Payments and B4. Keep `unresolved` when a lease is re-claimed instead of writing `submitting` again. The screens tolerate the flicker either way.
- H5, Payments. Confirm that a failed attempt with a submission means only a finalized execution error. Until then the network-rejected reason says the organizer's wallet may have paid a fee. errors.ts maps that failure to `RPC_UNAVAILABLE` and says "Devnet USDC" rather than "test USDC".

## Done when

- [ ] Refreshing during signing or submission restores the same attempt.
- [ ] A transaction reference by itself never produces a success receipt.
- [ ] An unresolved outcome has no action that silently starts another payment.
