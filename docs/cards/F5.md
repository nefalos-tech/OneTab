## Outcome

Participants see the confirmed result or an accurate explanation of what remains unresolved.

## Start and handoffs

Build pending, failed, expired, unresolved and confirmed views against fixtures before the real RPC flow is ready.

Implementation prerequisites: [F3](https://github.com/nefalos-tech/OneTab/issues/9), [F4](https://github.com/nefalos-tech/OneTab/issues/10)

Needed for final integration: [P4](https://github.com/nefalos-tech/OneTab/issues/4).

## Work

- [ ] Show pending, confirmed, failed, expired and unresolved as distinct states from the server.
- [ ] Render a receipt only for confirmed success. Include seller, total, payer shares, transaction reference and Devnet explorer link.
- [ ] Restore the existing attempt after reload. Continue checking the same transaction after connection loss.
- [ ] Allow restart only when the server says the prior attempt is safely resolved and fresh approvals are required.
- [ ] Explain insufficient USDC/SOL and rejected prompts with a next action. Do not display a misleading successful or canceled state.

The result screen is a pure view of the public room. A receipt shows only when the room is paid, its spots are exactly 1 to the payer count, each on its own wallet and approved, and the receipt names the attempt's own reference as a 64-byte signature, this checkout's seller and total, and every share in spot order, adding up to the total. Anything less reads Finalizing, and the explorer link is built from the reference. A failed payment's reason comes from the stop reasons in `src/client/catalog.ts`: network rejected when it was sent, else the room's error code, else the cause this page's own Start or Try again heard for that exact attempt, else a line that says it stopped before it was sent. Try again runs the same start path as Start, naming the attempt it replaces, and is offered only to the organizer of a failed or expired attempt with `canRetry`. A success moves everyone to the room, where a new attempt needs every approval again. Start and Try again read the room inside their own write, so no poll shows a room while they answer, and what they say follows from the start's answer and that room, as architecture.md tabulates. A refusal's cause binds to the first room of its own checkout that shows the failed attempt. Another checkout's room or the next Start or Try again press drops it. A Try again refused again says so in a notice about the new attempt.

Until F2's wallet adapter, P4, B4 and handoff H1 land, the evidence is unit tests with a stubbed fetch, the e2e suite on the fake API's scripted rooms, and a browser run of the signed-in organizer's paths against a stand-in API. results.spec.ts holds a move's page in its loading skeleton through the fake API's `holdServerReads`, leaves by the header link, and checks that Back to that page neither moves the viewer nor focuses its status block. The e2e guard refuses every browser write, so the paths that need one stay harness-only: a refused Start or Try again reaching the screen through `LiveCheckout`'s note subscription, the keyed notice when Try again is refused again, the move after this page's own write, the move on the next poll after a write whose own read failed, and the fresh adversary's X1, R1, R2 and R3 runs. Unit tests cover each of them below the component, but removing the note subscription in viewer.tsx still leaves every committed test green, as the recovery rerun's M3 showed, so only the harness catches that. A live 422, a live retry, a real receipt and H1 in the hosted app are not run yet.

Only `checkout-view.ts` mints a `Replaceable` or a `VerifiedReceipt`. Neither brand is exported, a lint fence refuses a cast or an import that names one, and `src/client/brand-fence.test.ts` proves the fence. Three paths still type-check without tripping it. The first is a cast to an exported type that holds a brand, such as `as Action`, `as ActionOf<"retry">` or `as Recovery`, or a generic `as T` helper, and the fence test pins that it passes lint. The second is a cast to an indexed-access type that resolves to a brand without naming it, such as `Extract<Recovery, { kind: "organizer_can_retry" }>["retryOfAttemptId"]`. The third is a value typed `any`, such as a `JSON.parse` result, given to a branded field. Review has to catch those. The PR uses `Refs #11`, and this card stays open until that live proof exists.

Handoffs from F5:

- H1, B3 (@SophiaChua). Project `observed_error` as `error.code` when it is an `ErrorCode`, and `INVALID_PAYMENT` otherwise (`b3_rooms.sql:71`). Never emit any other value, because the server parses rooms with the client parser and one unknown code fails every room read. Then every viewer sees the cause with no client change. It also tells anyone with the link that a payer was underfunded, though not which one, so spec.md records that choice first.
- H2, B3. Coalesce the receipt subquery (`b3_rooms.sql:72-73`), so a missing receipt row keeps the attempt with `receipt: null` instead of dropping it.
- H3, Payments (@kyusuku) and B4. Resolve a declined attempt, or a signing attempt past its blockhash, as `expired` with `safelyResolved` once it can't land, and wire `backendAssurance` so `expired` is reachable.
- H4, Payments and B4. Keep `unresolved` when a lease is re-claimed instead of writing `submitting` again. The screens tolerate the flicker either way.
- H5, Payments. Confirm that a failed attempt with a submission means only a finalized execution error. Until then the network-rejected reason says the organizer's wallet may have paid a fee. errors.ts maps that failure to `RPC_UNAVAILABLE` and says "Devnet USDC" rather than "test USDC".
- H6, Payments. Carry the new attempt's id in a 422, 400 or 503 answer to a start or a Try again. The page then needn't infer which attempt failed from the next room it shows, and a second organizer tab can't take the note.
- H7, B1. The confirmed room fixture's reference is 87 characters that decode to 63 bytes, not a 64-byte signature, so the page reads that room as Finalizing. A real signature there would make it read Paid.

## Done when

- [ ] A transaction reference by itself never produces a success receipt.
- [ ] An unresolved outcome has no action that silently starts another payment.
